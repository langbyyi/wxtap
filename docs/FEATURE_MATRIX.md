# WxTap 功能矩阵

该矩阵描述 WxTap 的生产入口。

> 本表按**功能**分组，比界面导航更细一层：界面的「流量」= 这里的「捕获」+「数据」，界面的「代码」= 这里的「分析」。
> 两者刻意采用不同口径——捕获与数据的**数据策略**不同（实时查看 vs 长期保留），合并成一行则无法说明。
> 界面导航的分组见 [../README.md](../README.md#能力总览)。

| 工作区 | 前端入口 | 后端能力 | 数据策略 |
| --- | --- | --- | --- |
| 连接 | `/control` | `engine.*`、`wechat.status`、`config.*` | 状态事件 + 1 秒微信宿主检测；`/targets` 已并入调试组的 `/devtools` |
| 捕获 | `/wxapi`、`/cloud` | `wxapi.*`、`cloud.*` | 连接不采集，钩子由「开启捕获」安装，自安装之时起记录；「停止捕获」的顺序是 停投递 → 清页面缓冲 → 卸载钩子 → 清 shell 待投递（已入库的仍在历史记录里）。实时队列有上限；记录带 `rid`，事件与 poll 双路投递幂等（同一 `rid` 只渲染一行）；落定更新流原地覆写状态/正文/耗时，过载时 `*.stats` 报告 shell 与页面侧丢弃 |
| 数据 | `/traffic` | `traffic.list`、`traffic.getBody`、`traffic.stats`、`traffic.clear`、`traffic.delete` | SQLite 页码分页（最新在前，后端给总数），正文按需读取；勾选批量删除或按 id 删单条之外，可「清空」全部记录（确认框写明条数与不可恢复）；库不再自动裁剪 |
| 调试 | `/navigator`、`/console`、`/devtools`、`/vconsole`、`/hook` | `navigator.*`、`console.*`、`hook.*`、CDP、`engine.vconsole` | 当前路由与拦截状态以后端回读为准（拦截器随页面 realm 消失，须回读校准）；console 环形缓冲有上限。注入脚本可反复重注（文件每次从磁盘重读），成功后行内回显上次落定值/错误与耗时、`stale` 标出「文件在注入后又被改过」，这些是壳侧登记的事实、跨 realm 保留，而 `injected` 随 realm 重建复位；脚本在小程序页面上下文中执行、被包在一层作用域内，其 `console` 带 `[文件名]` 前缀进 Console 页。vConsole 只有开关：面板位于小程序窗口内，本程序无法读取其内容，日志/请求走 Console、WxAPI、云函数、历史记录页 |
| 分析 | `/extract`、`/code` | `extract.*`、`code.*` | 长任务发出 `task` 事件；命中原文直接展示（本地排查用），脱敏值只用于搜索匹配 |
| 利用 | `/sessionkey`、`/ak` | `sessionkey.*`、`ak.verify`、`wxopen.*` | 每次调用由用户显式触发；凭据只在内存；官方接口的请求与响应按原文展示；不提供消息类官方接口 |
| 系统 | `/settings`、`/mcp` | `config.*`、`settings.*`、`mcp.*` | 独立端口与资源路径诊断 |
| 帮助 | `/faq`、`/feedback` | `fetch.md`（**只服务「交流反馈」页**；「使用帮助」是内置静态内容，不走 IPC） | 内容失败时显示可恢复错误；「交流反馈」另有上次成功内容的本地缓存，拉取失败时仍可读 |

## 端口

四个端口里只有 9421 是固定的（协议常量），其余三个都能在界面上改：

- 微信 WMPF 调试通道：`9421`（**固定**，Core 监听、小程序拨入，不可配）
- CDP 代理：`31415`（可配，缺省值；「状态」页的「CDP 端口」，1–65535）
- 云函数转发（Cloud API）：`27182`（可配，缺省值；「云函数」页的「API 端口」，1024–65535）
- MCP 服务（Streamable HTTP `/mcp` + legacy SSE `/sse`）：`9527`（可配，缺省值；「MCP 服务」页）

## 关键验收约束

- 历史流量不得一次性加载全部记录；列表使用页码分页，一次只持一页。
- 请求/响应正文只有在用户查看详情时读取。
- 异步调用的落定结果（状态、返回正文、耗时）必须能在 drain 之后原地回写；记录身份 `rid` 与 `traffic_records.id` 同源，事件流与 `poll` 双路投递对同一 `rid` 幂等（不得出现重复行）。
- 反编译、扫描、导出等长任务必须能显示阶段、进度和失败原因。
- 启停类操作（wxapi 捕获 / 云函数捕获 / 云函数 API 服务 / 引擎 / MCP 服务 / vConsole / 页面遍历，**七处**）各只有**一个**开关按钮：标签说明按下后会发生什么，关着写「开启…」、开着写「停止…」，在飞时写「…中…」并禁用；不得并排两个启停按钮。统一使用 `components/StateToggle.vue`。
- AK、SessionKey、请求头与 Token 按原文渲染（本地排查工具，掩码会使「签名算错」与「值看错」相互混淆）；落盘路径仍由后端策略管控。
- `Call` 错误返回结构化 `code/message/retryable`，旧字符串错误仍兼容。

## 需求编号对照（R1–R15）

代码与测试的注释里用 `R<n>` 指代**大流量捕获那一轮**冻结下来的验收要求（`hookfeeder.go`、`contracts/traffic.ts`、几个视图与契约测试里都有引用）。原表随那一轮的设计稿归档，这里保留一份可解析的对照，避免注释中只剩无法追溯的编号。

同一批注释里还会出现 `roadmap 2.x` / `路线图 §2.x`：那是同一份设计稿的**章节号**，与 `R<n>` 同源不同粒度，而非另一套需求。已见到的引用覆盖 2.1（记录身份 `rid` 的第二段、清空顺序）、2.3（历史记录页与 `traffic.stats` 的冻结形状、AppID 展示口径、翻页不得弹回页首）、2.4（丢弃计数即 R12；2.4b 是 VACUUM 阈值）、2.5（agent 面按 `appId` 筛选）与 §4（跨层容量镜像：页面两条缓冲的重投递窗口必须落在 shell 去重 FIFO 之内）。这套编号并未逐条归档，遇到未列出的条目按就近的 R 条目对照。

| 编号 | 要求 |
| --- | --- |
| R1 | `install()` 的 `ok` 必须是**累计**语义 |
| R2 | 更新流的续行取数（规格漏实现的那条） |
| R3 | 前端孤儿更新帧缓冲 |
| R4 | 批量队列的丢弃必须可见 |
| R5 | `Clear()` 必须作废在途 drain 页 |
| R6 | 落定更新不得破坏已有数据 |
| R7 | 前端小缺陷 |
| R8 | 测试质量 |
| R9 | 记录流也要有每 tick 轮数预算（`maxUpdateRounds` 镜像它） |
| R10 | `Clear()` 的作废语义要覆盖三条路径 |
| R11 | 重投递去重 FIFO 必须覆盖更新流（容量关系是跨层不变量） |
| R12 | **页面侧丢弃计数**：`drain` 响应带累计 `droppedRecords` / `droppedUpdates`，`FeederStats` 透出为 `pageDropped*`。注意两个面板口径不同：**历史记录页**把它与 shell `dropped` 相加（`traffic.stats` 的合并读数），而**捕获页**刻意分成两个读数、不相加 —— 「已丢弃」是页面侧的永久丢失，「未进列表」是 shell 待投递溢出，合成一个会掩盖「数据丢失」与「仅未显示」的区别（跨层口径见 [ARCHITECTURE.md](ARCHITECTURE.md) 的「主要链路」第 4 条） |
| R13 | 容量镜像不变量改为跨层读取 |
| R14 | 前端队列上限按推导取值（R14b：补 `wxapi_update` 数组载荷的测试） |
| R15 | 评论与实现对齐 |

新增或改名计数口径前先读 R12：字段名 `droppedRecords` / `droppedUpdates` 是**冻结名**，改它们等于改前后端契约。
